## [Unreleased]

### Lean core

The repository was reduced to a small detection core: ingestion from Wazuh, Zeek, Suricata, syslog and a JSON webhook, OCSF normalization, Sigma rule evaluation, detections, incidents, event search and ATT&CK coverage. Entries below this section describe earlier versions and mention features that no longer exist.

Read the upgrade notes in `INSTALL.md` before you upgrade an existing installation.

#### Added

- First login without a built-in password. On an empty database the backend creates one account, `admin@mxtac.local`. Its password is `INITIAL_ADMIN_PASSWORD` when set, otherwise a random one that is written once to the startup log. The account must set a new password at the first sign-in, and the login page has a step for it.
- `SEED_DEMO_DATA` setting. `true` also creates demo accounts for the analyst, hunter and engineer roles and invented sample data. The default is `false`.
- `POST /api/v1/auth/password`: a signed-in user changes the own password. The UI has a form under **Settings**, **Profile and security**.
- Silent session refresh in the web UI. When the access token has expired, the UI obtains a new one with `POST /api/v1/auth/refresh` and repeats the request; requests that fail together share one refresh, and the alert stream reconnects with the new token. The user is signed out only when the refresh is refused, and the login page then shows "Your session has ended. Sign in again." and returns to the page that was open.
- Refresh token rotation with reuse detection. Every refresh issues a new refresh token and invalidates the one that was used. A refresh token that is presented twice ends its session.
- A password change ends every session of the account. `users.token_version` (migration `0028`) is increased, and tokens issued before are refused. Sign-out ends the refresh token of the session as well as the access token.
- `REFRESH_COOKIE_SECURE` setting (default `true`).
- A detection records the event that caused it. The normalizer pipeline assigns every event its ID, the event is stored under it, and the detection carries it as `event_id`. The detection side panel has an "Open event in Hunt" action, and Hunt opens one event from its address (`/hunt?event=<id>`), which can be shared.
- MITRE ATT&CK technique names. The backend bundles a table of the Enterprise techniques and sub-techniques (ATT&CK v20.1, `app/backend/app/data/attack_techniques.json`, generated by `scripts/gen_attack_techniques.py`). Detections carry the technique name, also those stored by earlier versions; heatmap rows carry it; `GET /api/v1/attack/techniques` serves the table to the UI, which shows names in the coverage lists and matrix, incidents and rule tags.
- `NOTICE` file with the MITRE ATT&CK attribution and license.
- Login and refresh responses contain the `email` and `role` of the account.
- Normalizers for syslog and for generic webhook events. Events from all five source types are stored, searchable and evaluated by Sigma rules.
- 20 bundled Sigma rules in `app/backend/sigma_rules/`, most of them for Linux syslog events. They are imported into the `rules` table at startup with the source `bundled`, are listed on the Sigma Rules page and count towards coverage.
- Sigma engine: nested parentheses, `1 of`, `all of` and `<n> of` with `them` or a name pattern, wildcards `*` and `?`, list-of-maps selections, tactic tags by name (`attack.credential-access`), and rule selection by `product`, `category` and `service`.
- New web UI built on a design-token system: CSS variables in `src/index.css`, Tailwind color mapping, base components in `src/components/ui/`.
- Light and dark themes. The first visit follows the operating system setting.
- Rebuilt pages: Overview, Detections, Incidents, Hunt, ATT&CK Coverage, Sigma Rules, Sources, Settings, Login.
- Favicon and page title for the frontend.
- `README.md` with a quick start, and a documentation set under `docs/`: architecture, API reference, Sigma engine, ATT&CK coverage, integration guide, UI, security, deployment, development.
- `scripts/gen_rule_table.py`, which generates the table of bundled rules in `docs/sigma-engine.md`.
- `.gitattributes` that keeps shell scripts in LF line endings.
- `MXTAC_HOST` variable for `app/setup.sh`.
- `app/frontend/nginx.conf` for the production frontend image: fallback to `index.html` for client-side routes, and a proxy for `/api` including the WebSocket upgrade.
- `VITE_PROXY_TARGET` for the Vite dev server (default `http://localhost:15000`), so that the frontend can run on the host.
- `HTTP_PORT` and `HTTPS_PORT` for `app/docker-compose.prod.yml`.

#### Changed

- The refresh token is no longer part of a response body. `POST /api/v1/auth/login`, `/auth/mfa/verify`, `/auth/change-password` and `/auth/refresh` set it as the cookie `mxtac_refresh` (HttpOnly, Secure, SameSite=Strict, path `/api/v1/auth/refresh`), and `POST /api/v1/auth/refresh` reads it from there instead of the body. API clients that refreshed with a body have to keep the cookie. See `docs/security.md`, "Sessions".
- `POST /api/v1/auth/password` answers `200` with a new session instead of `204`, because the change ends the session that made the request along with all others.
- A new detection stores the ATT&CK technique name in `technique_name`, or the technique ID when the technique is not in the bundled table, instead of the rule title.
- The role and the active flag of an account are read from the database on every request. A role change or a deactivation takes effect at once, also for tokens that were issued earlier.
- The alert WebSocket `/api/v1/ws/alerts` requires a valid access token in the `token` query parameter. Other connections are refused.
- The web UI stops reconnecting the alert stream when the server refuses the token, and shows the stream as offline.
- `POST /api/v1/users` always creates the account with a forced password change at the first sign-in.
- The Sigma engine loads rules from the `rules` table only. Unsupported syntax (aggregations, `timeframe`, correlation rules, unknown modifiers) is rejected with an error when a rule is created, imported or tested, instead of being stored and never matching.
- API responses contain real data only. A new installation shows zeros and empty states. The coverage trend no longer contains generated history.
- `RATE_LIMIT_PER_MINUTE` sets the limit for read requests.
- `OPENSEARCH_USERNAME` and `OPENSEARCH_PASSWORD` are used for the OpenSearch connection.
- `QUEUE_BACKEND` accepts `memory` and `redis`.
- `app/docker-compose.yml` applies database migrations before the backend starts.
- `app/docker-compose.prod.yml` and `app/nginx/nginx.conf` now form a working stack: OpenSearch service, migrations at backend start, the frontend served from its own container, a WebSocket location, and the certificate file names `server.crt` and `server.key`.
- `app/setup.sh` runs the migrations when the backend starts, prints how to sign in for the first time, and no longer contains a fixed IP address. Its Nginx configuration sets the client address for the backend rate limits.
- `app/update.sh` no longer overwrites the generated Compose file and Nginx configuration, and runs the migrations before it starts the new backend.
- The Nginx configurations do not write the alert WebSocket request, which carries the access token, to the access log.
- Backend container health checks use Python instead of `curl`, which is not in the backend image.
- The backend image now includes the migration files (`alembic/versions/` was excluded by `.dockerignore`).
- `app/deploy/systemd/mxtac.env.example` gives `CORS_ORIGINS` as a JSON array.
- `CONTRIBUTING.md` replaces the governance and contributing guides. The numbered design documents at the repository root were replaced by the files under `docs/`.
- `INSTALL.md`, `ENV-REFERENCE.md`, `SECURITY.md` and `app/README.md` describe the current code.
- CI no longer installs `libxmlsec1`.

#### Fixed

Found by driving the web UI against a running stack:

- A rule that was created, edited, disabled or deleted did not take effect in the running engine until the next reload. The reload signal was sent before the change was committed, so the engine reloaded the old state.
- The event and error counts of a source were never stored: the Sources page showed 0 events for every source. A generic webhook source showed "Inactive" and "Never" after it had accepted events, and a disabled one still accepted events. It now refuses them with `403`.
- A new connector could stay in the status "connecting".
- `POST /api/v1/connectors` with a name that exists, and `POST /api/v1/rules` with an `id` that exists, answered `500`. They now answer `409` and `422` with a reason.
- A deactivated user disappeared from the Users tab and could not be reactivated there.
- Detections sorted by severity were ordered by the name of the level. Lists sorted by a column with equal values could repeat or skip rows between pages.
- A detection carried no user, process or log source of the matched event, showed the rule title as technique name and the rule UUID under its name.
- A webhook event had no field for the process path, so the bundled LSASS rule could not match one. `process_path`, `image` and `exe` are now mapped.
- "Mean time to detect" was never filled in. It is now the time from the earliest linked event to the creation of the incident.
- The Hunt page hit the write rate limit after about 20 searches a minute and then reported a syntax error. Its event queries now count as read requests, and a failed search shows the reason.
- The Sigma Rules and Sources pages showed "Could not load" to roles without access. They now show a notice, like the Hunt page.
- The import dialog closed without showing why a rule was skipped.
- The Overview page did not show a new detection until its next 60-second refresh.
- `POST /api/v1/auth/mfa/verify-setup` accepted a code only inside its own 30 seconds. It now has the same tolerance of one time step as the sign-in.
- The `/` shortcut did nothing. Sign-in now returns to the page that was asked for.
- Dates and durations were written in three different forms. Incidents showed tactic IDs instead of names. The `X-Frame-Options` meta tag, which browsers ignore and report as an error, was replaced by a response header in `app/frontend/nginx.conf`.

- Migration `0008` failed on PostgreSQL. `alembic upgrade head` now works on an empty PostgreSQL database.
- The Vite dev server forwards the alert WebSocket.
- Hunt search with OpenSearch as the search backend. The event persister now indexes the same document the API returns (the flat fields `hostname`, `username`, `src_ip`, `dst_ip`, `source`, `summary` and so on, plus the nested event) into `mxtac-events-v2-*`, with an explicit mapping. Search, aggregation and CSV export return the same rows from OpenSearch and from the PostgreSQL fallback: free text is a case-insensitive substring of the summary, class, host, user, addresses or process command line, and every filter field and operator works on both. Before, free text only matched an exact class name, rows had no host, user, addresses, source or summary, and the host filter only looked at the source endpoint.
- A failed OpenSearch query is answered from PostgreSQL instead of with an empty result.
- Events of an installation with event indices of an earlier version are re-indexed from PostgreSQL at startup.
- The free-text search also matches the process command line. `contains` works on the numeric fields `severity_id` and `class_uid`.
- Detections created by the pipeline store the tactic name in `tactic` (the ID stays in `tactic_id`), so they appear in the Overview tactic list and heatmap and match the tactic filter on the Detections page. Existing detections that hold the tactic ID are read as the tactic they name.
- A rule with the level `informational` creates a detection with the severity `low`. Before, such a detection made `GET /api/v1/detections` fail.
- The WebSocket alert subscriber and the rule-reload subscriber no longer time out on an idle Valkey subscription. Before, the backend logged `Valkey subscriber error, reconnecting in 1s` every few seconds and could miss an alert published during the reconnect, and a rule change on one backend replica did not reach the others.
- Background tasks started at startup are referenced until they end and are cancelled at shutdown, so a subscriber that waits for a message without a timeout is not garbage-collected.

#### Removed

- The four default accounts with a shared, published password.
- `POST /api/v1/users/invite`, the `SMTP_*` settings and the `aiosmtplib` dependency.
- The Kafka queue backend, the `KAFKA_*` settings and the Redpanda container in the Compose files and `app/setup.sh`. A `.env` file that still contains `KAFKA_*` or `SMTP_*` settings stops the backend at startup.
- The scheduled detection engine service. Detection happens in the streaming pipeline.
- Placeholder data in API responses and the generated coverage history.
- SSO (OIDC and SAML).
- Threat intelligence and IOC management, including the OpenCTI connector.
- Compliance views, reports and scheduled reports.
- Asset inventory.
- Notification channels and alert outputs (email, syslog, webhook, file).
- NDR views and the endpoint and network agents API.
- The Rust endpoint and network agents and their directory.
- Admin console, permission sets and API keys.
- Prowler and Velociraptor connectors.
- Hunt suggestions, suppression rules and alert auto-close.
- DuckDB event store.
- The `matrix` UI theme.
- The unused `VITE_API_BASE_URL` build variable and `app/frontend/.env.example`. The frontend calls the API with relative URLs.
- Planning documents, task summaries, UI design drafts and third-party dashboard examples from the repository root.

## [2.0.0-alpha] — 2026-02-23

Initial alpha release of the MxTac platform (Matrix + Tactic). This release
establishes the core backend, frontend, detection engine, and CI/CD foundation.

### Added

#### Backend (FastAPI / Python 3.13)
- FastAPI application with versioned API under `/api/v1/`
- JWT authentication (access + refresh tokens) with key-version invalidation
- Role-based access control (RBAC) — `admin`, `analyst`, `hunter` roles
- Account lockout after 5 failed attempts (30-minute window)
- Inactive account auto-lock after 90 days
- Password history — cannot reuse last 2 passwords; 90-day expiry policy
- First-login forced password change
- SSO via OIDC (Keycloak, Okta, Azure AD) and SAML 2.0
- SQLAlchemy 2.x async ORM with Alembic migrations
- PostgreSQL primary datastore; SQLite single-binary fallback mode
- Pydantic v2 request/response schemas with strict validation
- Repository pattern for all data access (alerts, rules, users, tenants)
- Service layer with clear separation from persistence
- Sigma detection engine — native rule loading, evaluation, ATT&CK tagging
- Event ingestion pipeline with in-memory and Redis/Valkey queue backends
- Kafka queue backend (optional, configurable via `QUEUE_BACKEND`)
- OpenSearch integration for event storage, full-text search, and ILM retention
- DuckDB embedded event store — local analytics without OpenSearch
- Asset auto-discovery from ingested events (CMDB upsert, RFC 1918 only)
- OpenSearch snapshot management with configurable retention
- Alert output sinks: file (JSON Lines, rotating), webhook (POST, retry), syslog, and email (SMTP)
- Alert enrichment — GeoIP (MaxMind), OpenCTI threat intel, IOC matching
- Alert deduplication — MD5(rule_id + host) key with 5-minute Valkey TTL window
- Risk scoring — severity × 0.60 + asset criticality × 0.25 + recurrence × 0.15
- Alert-to-incident auto-correlation — group by (host, tactic) within 1-hour window
- Escalation policy — auto-escalate unacknowledged critical/high alerts after 30 minutes
- Notification senders — email (SMTP + STARTTLS) and Slack (webhook)
- Dead letter queue — failed events routed for inspection and replay
- Back-pressure handling — slow ingest when queue is full
- Connectors: Wazuh, Zeek, Suricata, Prowler, Velociraptor, OpenCTI (base connector ABC + implementations)
- Custom field mapping config per connector
- `POST /connectors/{id}/test` — health check endpoint
- API key management — create keys with scoped access (read / write / admin)
- `POST /users/invite` — send email invitations to new users
- Rate limiting middleware (configurable per-minute threshold)
- CORS middleware with explicit origin allowlist
- `/health` and `/ready` liveness/readiness probes
- Structured logging (JSON-formatted, no sensitive field leakage)

#### Frontend (React 19 / TypeScript / Vite)
- React 19 with TypeScript strict mode
- Tailwind CSS v4 design system
- Zustand state management stores
- `lib/api.ts` typed API client with error handling
- Authentication flow (login, token refresh, session persistence)
- ATT&CK coverage dashboard — technique heatmap, tactic breakdown
- Alert management — list, detail, acknowledge, filter by severity/technique
- Sigma rule management — browse, enable/disable, upload
- Role-aware UI — route guards, permission-based component rendering
- Vitest + Testing Library unit and integration tests

#### Agents (Rust / Tokio)
- **mxguard** — EDR agent for endpoint event collection
- **mxwatch** — NDR agent for network metadata collection
- Async Tokio runtime; structured event emission to backend pipeline

#### Agent Scheduler
- Next.js frontend for scheduling Claude Code agent tasks
- FastAPI backend with SQLite persistence (aiosqlite)
- Configurable concurrency, retry, timeout, and backoff parameters
- Optional HTTP Basic auth (`AUTH_PASSWORD`)

#### Infrastructure & Operations
- Docker Compose stack for development (`app/docker-compose.yml`)
- Production Docker Compose with Nginx reverse proxy (`app/docker-compose.prod.yml`)
- GitHub Actions CI pipelines:
  - Backend: lint (Ruff, mypy) + pytest
  - Frontend: lint (ESLint) + test (Vitest) + build (Vite)
  - Docker: build and push to GitHub Container Registry
- Dependabot configuration for automated dependency updates
- Trivy vulnerability scanning on every push
- Secret rotation procedures and environment hardening guide

#### Detection
- Sigma rule loader — YAML parsing, compile-time validation
- ATT&CK technique tagging from Sigma rule `tags` field
- Coverage calculator — per-tactic and per-technique detection percentage
- Sample Sigma rules for common ATT&CK techniques

#### Governance & Documentation
- `CHANGELOG.md` — this file
- `SECURITY.md` — vulnerability disclosure policy
- `LICENSE` — GNU Affero General Public License v3.0 (AGPL-3.0)
- `.editorconfig` — consistent formatting across editors
- `app/frontend/.prettierrc` — Prettier code style config
- `ENV-REFERENCE.md` — complete environment variable reference
- API versioning strategy documented in `06-API-SPECIFICATION.md`

### Fixed

- Soft-delete users: set `is_active=False` instead of hard delete to preserve audit trail
- Scheduler: corrected GitHub repository URL for agent task runner

### Security

- Passwords hashed with Argon2id (via `passlib`)
- JWT secrets validated at startup; dev default rejected in production
- Sensitive fields (`SECRET_KEY`, DSN passwords) excluded from logs and repr
- CORS restricted to explicit `CORS_ORIGINS` allowlist
- SQL injection prevention via SQLAlchemy parameterised queries
- XSS mitigation via React DOM escaping + strict Content-Security-Policy headers
- Dependabot and Trivy integrated for supply-chain and CVE scanning
